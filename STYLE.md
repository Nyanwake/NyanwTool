# NyanwTools - Coding Style Guide

This document defines the coding style and development rules for the NyanwTools Blender addon.

The goal is to keep the codebase clean, maintainable, and easy to extend over many versions.

---

# General Principles

Write code for long-term maintenance.

Always prefer readability over clever solutions.

Keep the addon simple.

Avoid unnecessary abstraction.

Avoid unnecessary settings.

Avoid unnecessary automation.

The addon is used daily by one experienced VTuber creator.

Optimize for workflow speed, not for maximum flexibility.

---

# Project Architecture

Each module has a single responsibility.

ui.py

    User Interface only.

operators.py

    Blender Operators only.

presets.py

    Blendshape preset definitions only.

mirror.py

    Blendshape mirroring logic only.

derived.py

    Blendshape generation from existing Blendshapes.

Never place business logic inside ui.py.

UI should only display data and call operators.

---

# Naming

Use English only.

Use descriptive names.

Good:

CreateBlendshapesOperator

BlendshapePreset

separator_name

blendshape_count

Bad:

Create

Temp

Data1

Test

---

# Variables

Use snake_case.

Example:

current_shape_key

missing_blendshapes

separator_name

Never use abbreviations unless universally understood.

Avoid single-letter variables.

Except:

i

x

y

inside short loops.

---

# Classes

One class = one responsibility.

Avoid large classes.

If a class grows too much, split it into smaller modules.

---

# Functions

Functions should do one thing.

Prefer many small functions over one large function.

Good:

calculate_status()

create_separator()

find_missing_blendshapes()

Bad:

do_everything()

---

# UI Rules

Never hardcode Blendshape names inside ui.py.

Everything displayed by the UI must come from presets.py.

The UI should not calculate Blendshape status.

The UI only displays calculated information.

---

# Presets

presets.py contains data only.

Preset data may contain:

- Display name
- Separator title
- Blendshape list

Preset data must never contain:

- UI state
- Icons
- Colors
- Completion status
- Blender objects

Status is calculated dynamically.

---

# Separators

Separator formatting is generated by code.

Presets only store the separator title.

Example:

Eyes

The addon creates:

════ Eyes ════

Never hardcode separator formatting inside preset data.

---

# Operators

Every button should call a Blender Operator.

Operators perform all scene modifications.

Never modify Blender data directly from UI code.

---

# Icons

Icons are loaded once during addon initialization.

Status icons are selected dynamically.

Current status icons:

green.png

yellow.png

red.png

logo.png

Preset data never references icons.

---

# Status Calculation

Status should always be calculated from the current object.

Never cache status.

Possible states:

Green

All Blendshapes exist.

Yellow

Some Blendshapes exist.

Red

No Blendshapes exist.

---

# Mirror System

Always use Blender's native Blendshape Flip.

Do not implement a custom mirror algorithm.

Automatically detect:

Left ↔ Right

The operator should create the missing destination Blendshape if necessary.

---

# Combine System

Always use Blender's native "New Shape From Mix".

Do not recreate Blender functionality.

The addon should automate workflow, not replace Blender features.

---

# Error Handling

Fail safely.

Never crash because a Blendshape is missing.

Provide clear error messages.

Never silently modify user data.

---

# Code Duplication

Avoid duplicated logic.

If the same code appears twice, move it into a shared function.

---

# Future Development

Every new feature should answer one question:

"Does this reduce repetitive work?"

If not, it probably does not belong in NyanwTools.

Keep the addon focused.

Do not turn it into a general-purpose Shape Key toolbox.

It is a VTuber production tool.

---

# AI Development Rules

When modifying this project:

- Preserve the existing architecture.
- Do not rewrite working systems unless requested.
- Keep code modular.
- Keep functions short.
- Prefer extending existing systems instead of replacing them.
- Avoid introducing unnecessary dependencies.
- Follow Blender API best practices.
- Preserve naming conventions.
- Maintain backward compatibility whenever possible.

Always assume that this project will continue growing over time.
